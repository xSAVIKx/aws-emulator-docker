The AWS Emulator, ready to run in Docker.

AWS does not publish a prebuilt image of its local AWS API emulator. This project builds one, tests it on both architectures, signs it, and publishes it to three registries. A workflow checks for a new upstream release every hour and publishes a new image in about one to two hours.

A quick health check only. For SDK use, follow the quick start.

docker run --rm -p 127.0.0.1:9297:9297 ghcr.io/xsavikx/aws-emulator
Quick start Source on GitHub

A blog post about docker run, Compose, GitHub Actions and known problems: Running AWS Emulator in Docker, on any arch, in CI.

Multi-arch

Native amd64 and arm64 builds. Runs on Linux, on macOS (Intel and Apple silicon) and on Windows with Docker Desktop.

Verified upstream

A pinned upstream version, with an SHA-256 check and an RPM or DEB package signature check against the AWS signing key.

Signed

Keyless cosign signature, SBOM, SLSA provenance and a GitHub artifact attestation.

Tested

Each build runs STS and S3 calls and a health check on both architectures before it is published.

Quick start

The emulator writes its credentials, configuration and TLS certificate to ~/.aws/emulator/<port>/. Mount that directory, so your AWS CLI and SDKs can read the files.

Step 1. Create the directory. Step 2. Start the emulator.

mkdir -p ~/.aws/emulator
PORT=9297
docker run --rm --memory=2g --memory-swap=2g -p 127.0.0.1:$PORT:$PORT \
  --user "$(id -u):$(id -g)" \
  -e HOME="$HOME" -v "$HOME/.aws/emulator:$HOME/.aws/emulator" \
  ghcr.io/xsavikx/aws-emulator -p $PORT

With rootless Docker, container root maps to your host user. Your own UID, or no --user, fails with Permission denied (os error 13).

mkdir -p ~/.aws/emulator
PORT=9297
docker run --rm --memory=2g --memory-swap=2g -p 127.0.0.1:$PORT:$PORT \
  --user 0:0 \
  -e HOME="$HOME" -v "$HOME/.aws/emulator:$HOME/.aws/emulator" \
  ghcr.io/xsavikx/aws-emulator -p $PORT
New-Item -ItemType Directory -Force "$env:USERPROFILE\.aws\emulator"
$port = 9297
docker run --rm --memory=2g --memory-swap=2g -p "127.0.0.1:${port}:${port}" `
  -v "$env:USERPROFILE\.aws\emulator:/home/emulator/.aws/emulator" `
  ghcr.io/xsavikx/aws-emulator -p $port
# Usage:
#   mkdir -p ~/.aws/emulator
#   UID_GID="$(id -u):$(id -g)" docker compose up
# With rootless Docker, container root maps to your user:
#   UID_GID=0:0 docker compose up
services:
  aws-emulator:
    image: ghcr.io/xsavikx/aws-emulator:latest
    command: ["-p", "9297"]
    user: "${UID_GID:-1000:1000}"
    environment:
      HOME: ${HOME}
      EMULATOR_TELEMETRY: ${EMULATOR_TELEMETRY:-on}
    ports:
      - "127.0.0.1:9297:9297"
    volumes:
      - ${HOME}/.aws/emulator:${HOME}/.aws/emulator
    mem_limit: 2g
    memswap_limit: 2g
    restart: "no"

Start it with UID_GID="$(id -u):$(id -g)" docker compose up. With rootless Docker, use UID_GID=0:0.

Step 3. Point the AWS CLI or an SDK at the emulator.

export AWS_ENDPOINT_URL=https://127.0.0.1:9297
export AWS_SHARED_CREDENTIALS_FILE=~/.aws/emulator/9297/emulator_credentials
export AWS_CONFIG_FILE=~/.aws/emulator/9297/config
export AWS_CA_BUNDLE=~/.aws/emulator/9297/ca.pem
export AWS_EC2_METADATA_DISABLED=true
export AWS_DISABLE_HOST_PREFIX_INJECTION=true
export AWS_REGION=us-east-1 AWS_DEFAULT_REGION=us-east-1
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN AWS_PROFILE

aws sts get-caller-identity   # "Account": "000000000000"
$env:AWS_ENDPOINT_URL = "https://127.0.0.1:9297"
$env:AWS_SHARED_CREDENTIALS_FILE = "$env:USERPROFILE\.aws\emulator\9297\emulator_credentials"
$env:AWS_CONFIG_FILE = "$env:USERPROFILE\.aws\emulator\9297\config"
$env:AWS_CA_BUNDLE = "$env:USERPROFILE\.aws\emulator\9297\ca.pem"
$env:AWS_EC2_METADATA_DISABLED = "true"
$env:AWS_DISABLE_HOST_PREFIX_INJECTION = "true"
$env:AWS_REGION = "us-east-1"
$env:AWS_DEFAULT_REGION = "us-east-1"

aws sts get-caller-identity

Node.js needs NODE_EXTRA_CA_CERTS. Rust and .NET need SSL_CERT_FILE. Java needs truststore.p12. See the AWS SDK guide.

Important facts

Always publish the port on 127.0.0.1. The image binds to 0.0.0.0 inside the container, so a plain -p 9297:9297 exposes the emulator to your whole network.
  • Same port in three places. If you change the port, change the host side of -p, the container side of -p, and the emulator -p argument. Do not use -p 0.
  • TLS. The emulator creates a new self-signed certificate (ca.pem) at each start. Your client must trust that file.
  • Memory. Give the container 2 GiB. Above the limit, Docker stops it with exit code 137, and you lose all emulated resources.
  • No persistence. All state is in memory. A restart gives an empty emulator.
  • Health check. The image has a Docker HEALTHCHECK on /__admin/health. For another port, also set -e EMULATOR_HEALTHCHECK_PORT=<port>.
  • Telemetry. The upstream emulator sends anonymous usage telemetry by default. To turn it off, add -e EMULATOR_TELEMETRY=off.

Examples

Integration tests in six languages, with the most common test framework of each language and the official AWS SDK. Every example tests the same scenarios: STS identity, S3 objects, a DynamoDB table, an SQS queue, SNS to SQS fan-out, and a Secrets Manager secret. CI runs all of them on amd64 and arm64 every day and after each image release.

pytest + Boto3. Source and README.

import boto3
from botocore.config import Config

# Endpoint, keys, Region and CA come from the environment.
sts = boto3.client("sts")
s3 = boto3.client("s3", config=Config(s3={"addressing_style": "path"}))
sqs = boto3.client("sqs")

Two rules apply in every language: use path-style S3 addresses, and make sure SQS calls go to the emulator, not to the host in the queue URL. See the examples README.

GitHub Action

Run AWS Emulator on the GitHub Marketplace

The Run AWS Emulator action runs this image in your workflow. It waits until the emulator is healthy and sets the environment, so the AWS CLI and the SDKs in the next steps use the emulator with no code change. It works on Linux runners with Docker or Podman, x64 and arm64.

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: xSAVIKx/run-aws-emulator@v1
      - run: aws sts get-caller-identity   # "Account": "000000000000"
      - run: make integration-test         # your SDK tests use the emulator

Supported runners

Ubuntu 24.04 and 26.04 (GitHub-hosted): ubuntu-latest (x64), ubuntu-24.04 and ubuntu-26.04 (x64), ubuntu-24.04-arm and ubuntu-26.04-arm (arm64)Supported. The CI of the action tests the action on these runners on each change. The six language examples run every day and after each image release.

For reproducible runs, pin the image to a build tag or a digest:

      - uses: xSAVIKx/run-aws-emulator@v1
        with:
          image: ghcr.io/xsavikx/aws-emulator:__VERSION__

Inputs

Environment for the next steps

  • AWS_ENDPOINT_URL, AWS_SHARED_CREDENTIALS_FILE, AWS_CONFIG_FILE, AWS_REGION and AWS_DEFAULT_REGION point the CLI and SDKs at the emulator.
  • AWS_CA_BUNDLE and NODE_EXTRA_CA_CERTS contain the emulator CA.
  • SSL_CERT_FILE (system CAs + emulator CA) and JAVA_TOOL_OPTIONS (JDK CAs + emulator CA) are combined trust files. Downloads from Maven, NuGet and crates.io keep working in the same job.
  • Do not set AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY or AWS_PROFILE in the job. The SDKs use these before the emulator credentials file.

Each tag of the default variant has a matching tag with the -debian suffix and a matching tag with the -distroless suffix. The three variants install the same upstream emulator. The Amazon Linux variant uses the .rpm package. The Debian and distroless variants use the .deb package. The three variants use the same user, port and health check route.

The distroless variant has no shell, no package manager and no curl, so scanners report very few findings. Its health check is a small Go program. The other two variants use a shell script with curl. Its entry point is /opt/aws-emulator/bin/aws-emulator. The other two variants use aws-emulator from the PATH.

Verify the image

Each image has a keyless cosign signature from GitHub Actions. Use cosign v3 or later. Cosign v2 reports "no signatures found".

cosign verify ghcr.io/xsavikx/aws-emulator:latest \
  --certificate-identity 'https://github.com/xSAVIKx/aws-emulator-docker/.github/workflows/release.yml@refs/heads/main' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
gh attestation verify oci://ghcr.io/xsavikx/aws-emulator:latest --owner xSAVIKx --format json

The build checks the RPM or DEB package signature of the upstream package with the AWS package signing key, SSM Publishing <ssm-publishing@amazon.com>, fingerprint 98BC F336 A3BE 53B7 34E9 67C5 2E5B F49B D940 F624. Each base image is pinned by digest.

Frequently asked questions

What is the AWS Emulator?

The AWS Emulator is a local emulator of the AWS APIs from Amazon Web Services. It serves STS, S3, DynamoDB, SQS, SNS, Secrets Manager and many other services over HTTPS on 127.0.0.1, so tests and coding agents can run without an AWS account.

Does AWS publish a Docker image of the AWS Emulator?

No. The AWS guide tells you to build an image yourself from a short Dockerfile. This project builds that image for linux/amd64 and linux/arm64, tests it, signs it, and publishes it to GHCR, Docker Hub and Quay.io.

How do I run the AWS Emulator in Docker?

Create ~/.aws/emulator, then run: docker run --rm --memory=2g --memory-swap=2g -p 127.0.0.1:9297:9297 --user "$(id -u):$(id -g)" -e HOME="$HOME" -v "$HOME/.aws/emulator:$HOME/.aws/emulator" ghcr.io/xsavikx/aws-emulator -p 9297. Then set AWS_ENDPOINT_URL=https://127.0.0.1:9297 and the other variables from the quick start.

Does the image work on macOS, Windows and Apple silicon?

Yes. The image is a Linux image for amd64 and arm64. Docker Desktop runs it on macOS with Intel or Apple silicon and on Windows with the WSL 2 backend. Windows containers are not available, because the emulator runs only on Linux.

How do I use the AWS Emulator in GitHub Actions?

Add the step uses: xSAVIKx/run-aws-emulator@v1. The Run AWS Emulator action starts the image, waits until it is healthy, and sets AWS_ENDPOINT_URL, the credentials, and the CA settings, so the AWS CLI and the SDKs in the next steps use the emulator.

Why do my SQS calls with the AWS SDK for JavaScript v3 go to real AWS?

The emulator returns queue URLs with the real AWS host, for example https://sqs.us-east-1.amazonaws.com/000000000000/my-queue. The AWS SDK for JavaScript v3 sends SQS requests to the host in the queue URL. Set useQueueUrlAsEndpoint: false on the SQSClient. The SDKs for Python, Go, Java, .NET and Rust need no setting.

Why does the emulator fail with Permission denied on rootless Docker?

With rootless Docker, container user IDs map to other host user IDs, so the emulator cannot write to the mounted directory. Use --user 0:0, because container root maps to your own host user. With Podman, use --userns=keep-id.

Should I use localhost or 127.0.0.1 in AWS_ENDPOINT_URL?

Use 127.0.0.1. With a host name such as localhost, some SDKs use virtual-hosted S3 addresses such as bucket.localhost, which do not resolve. Also use path-style S3 addresses in your S3 client.

How do I verify the image?

Each image has a keyless cosign signature, an SBOM and SLSA provenance. Run cosign verify (version 3 or later) with --certificate-identity 'https://github.com/xSAVIKx/aws-emulator-docker/.github/workflows/release.yml@refs/heads/main' and --certificate-oidc-issuer https://token.actions.githubusercontent.com, or run gh attestation verify with --owner xSAVIKx.
